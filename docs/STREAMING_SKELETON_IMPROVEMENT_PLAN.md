# 스트리밍·스켈레톤 UI 개선 방향

## 1. 문제 정의

현재 PLAN, TASKS, DO, SEE 화면은 페이지 컴포넌트가 세션 확인과 DB 조회를 모두 마친 뒤 `PageHeader`를 포함한 전체 JSX를 반환한다. 이 때문에 간단한 제목과 설명문도 데이터 조회가 끝날 때까지 나타나지 않으며, 공통 설명문이 4초 이후 LCP 요소로 측정될 수 있다.

현재 `loading.tsx`는 화면 전체를 중앙 스피너로 대체한다. 로딩 중 실제 화면 구조를 알 수 없고, 데이터가 완료되는 순간 레이아웃이 한꺼번에 교체된다.

개선 목표는 다음과 같다.

- 제목과 설명 등 데이터와 무관한 화면 셸을 즉시 표시한다.
- 데이터가 필요한 큰 영역만 독립적으로 스트리밍한다.
- 실제 콘텐츠와 크기가 유사한 스켈레톤으로 레이아웃 이동을 방지한다.
- 스트리밍을 위해 동일한 DB 쿼리를 여러 번 실행하지 않는다.
- 권한 확인과 사용자 데이터 격리는 기존과 동일하게 유지한다.

## 2. 핵심 원칙

### 페이지 셸은 동기 렌더링

`PageHeader`, 정적인 설명, 화면 구조용 컨테이너는 가능한 한 동기 컴포넌트에 둔다. 데이터 조회는 별도의 비동기 서버 컴포넌트로 이동한다.

```tsx
export default function PlansPage() {
  return (
    <div className="flex flex-col gap-10">
      <PageHeader {...headerProps} />
      <Suspense fallback={<PlanGridSkeleton />}>
        <PlanGridData />
      </Suspense>
    </div>
  );
}
```

실제 구현에서는 인증되지 않은 사용자에게 셸이 잠깐 노출되어도 사용자 데이터가 포함되지 않아야 한다. 인증과 데이터 조회는 비동기 데이터 컴포넌트 안에서 다시 보장한다.

### Suspense는 섹션 단위로 배치

버튼, 배지, 카드 하나마다 경계를 만들지 않는다. 사용자가 하나의 콘텐츠 덩어리로 인식하는 영역을 기준으로 한다.

권장 경계:

- 계획 카드 그리드
- 할 일 목록
- 실행 기록 입력 영역
- 실행 기록 타임라인
- 선택 계획 요약과 별자리
- 통계 영역
- 회고 목록

### 쿼리 Promise를 공유

같은 페이지의 여러 스트리밍 영역이 동일한 계획·할 일·기록을 필요로 하면 각 컴포넌트에서 독립적으로 조회하지 않는다. 요청 단위로 메모이제이션한 loader 또는 공유 Promise를 사용한다.

```tsx
const loadSeeData = cache(async (userId: string, scope: SeeScope) => {
  // 한 번 조회한 결과를 별자리, 통계, 회고 영역이 공유한다.
});
```

React `cache()`는 사용자 사이의 영속 캐시 용도가 아니라 같은 서버 렌더 요청 안의 중복 호출 제거 용도로만 사용한다. 모든 loader는 반드시 검증된 `userId`를 입력으로 받아야 한다.

### 스켈레톤은 실제 레이아웃과 동일한 공간 확보

- 실제 카드 수를 알 수 없으면 대표적인 3~6개 자리만 표시한다.
- 최종 콘텐츠와 동일한 grid breakpoint를 사용한다.
- 별자리 영역은 최종 SVG의 aspect ratio와 최소 높이를 유지한다.
- 텍스트 줄은 실제 예상 길이에 가까운 여러 폭을 사용한다.
- 로딩 완료 시 컨테이너 높이가 급격히 바뀌지 않도록 한다.

### 애니메이션은 절제

기본은 낮은 대비의 고정 면 또는 느린 pulse를 사용한다. `prefers-reduced-motion`에서는 애니메이션을 제거한다. 별, 카드, 모든 텍스트 줄이 각각 강하게 반짝이는 형태는 피한다.

## 3. 공통 컴포넌트 방향

다음 공통 요소를 추가한다.

### `SkeletonBlock`

높이, 너비, radius, 추가 className을 받는 가장 작은 표현 요소다. 접근성 트리에 불필요하게 노출되지 않도록 `aria-hidden="true"`를 사용한다.

### `SectionLoadingState`

섹션 전체에 한 번만 `role="status"`, `aria-live="polite"`를 제공한다. 내부의 모든 막대가 각각 로딩 메시지를 읽게 하지 않는다.

### 화면 전용 스켈레톤

- `PlanGridSkeleton`
- `TaskListSkeleton`
- `WorkLogFormSkeleton`
- `WorkLogTimelineSkeleton`
- `ObservatorySkeleton`
- `SeeSummarySkeleton`
- `ReflectionListSkeleton`

화면 전용 스켈레톤은 실제 컴포넌트와 가까운 폴더에 둔다. 범용 스켈레톤 하나에 지나치게 많은 variant 조건을 추가하지 않는다.

## 4. 화면별 적용 방향

### PLAN `/plans`

현재 문제:

- 세션, 계획, 할 일, 수정 이력, 회고, 작업 기록 조회가 끝나야 헤더까지 표시된다.
- `loading.tsx`에서는 실제 카드 배치 대신 중앙 스피너만 보인다.

개선 구조:

1. `PageHeader` 즉시 표시
2. 계획 추가 버튼처럼 데이터가 필요 없는 action 즉시 표시
3. export/import처럼 계획 데이터가 필요한 action은 카드 데이터와 함께 로드하거나 별도 작은 경계를 사용
4. 계획 카드 그리드를 `PlanGridData` 비동기 컴포넌트로 분리
5. fallback으로 `PlanGridSkeleton` 표시

주의:

- 계획 조회와 카드 집계 쿼리는 현재 배치 조회 구조를 유지한다.
- 카드마다 별도 서버 쿼리를 실행하지 않는다.
- 빈 상태는 스켈레톤 완료 후 데이터가 0건일 때만 표시한다.

### TASKS `/tasks`

개선 구조:

1. `PageHeader` 즉시 표시
2. 검색·정렬 UI와 목록이 같은 데이터에 의존하는 범위를 확인
3. 태그 목록이 필요하면 필터와 목록을 하나의 비동기 영역으로 유지하거나 loader 결과 공유
4. 목록 영역에 `TaskListSkeleton` 적용

주의:

- URL query 기반 필터의 선택값은 셸에서 즉시 표현할 수 있다.
- 존재하는 태그 option만 DB 결과에 의존한다.

### DO `/do`

개선 구조:

1. `PageHeader` 즉시 표시
2. 활성 할 일이 필요한 입력 폼을 `WorkLogFormData`로 분리
3. 작업 기록 목록을 `WorkLogTimelineData`로 분리
4. 두 영역은 `Promise.all` 또는 요청 단위 loader를 공유
5. 각각 실제 크기에 맞는 스켈레톤 제공

주의:

- 두 영역을 독립적으로 스트리밍하더라도 활성 할 일 쿼리를 중복 실행하지 않는다.
- 작업 기록 전체 조회는 향후 페이지네이션 작업과 별도로 다룬다.

### SEE `/see`

가장 높은 우선순위다. 현재 순차 조회 단계가 가장 많고 별자리·통계·회고가 한 번에 나타난다.

개선 구조:

1. `PageHeader` 즉시 표시
2. 계획 선택 및 기간 선택 폼은 활성 계획 목록이 준비되는 즉시 스트리밍
3. 선택 범위 데이터 loader를 한 번 실행
4. 요약·별자리와 통계는 같은 loader 결과를 공유
5. 회고 목록은 필요한 경우 별도 Promise로 병렬 시작
6. 별자리 영역에는 고정 aspect ratio의 `ObservatorySkeleton` 사용

권장 경계:

- 범위 선택 폼
- 계획 요약 및 별자리
- 통계 카드
- 회고 입력 및 목록

경계를 네 개로 나누더라도 DB 요청을 네 번 복제해서는 안 된다.

### HOME `/dashboard`

현재 관측소 화면은 모든 활성 계획의 슬라이드 데이터를 준비한 후 렌더된다.

1차 개선:

- 관측소 전체 크기의 단일 `ObservatorySkeleton` 제공
- 개별 별이나 패널마다 경계를 만들지 않음

후속 개선:

- 홈 계획 한 개를 먼저 렌더
- 나머지 계획 슬라이드는 지연 로드

후속 개선은 캐러셀의 로딩 방식이 달라지므로 이번 스켈레톤 작업과 별도 배포한다.

## 5. `loading.tsx` 처리

페이지 내부 Suspense 경계가 준비되면 전체 화면 중앙 스피너는 해당 화면의 셸 스켈레톤으로 교체한다.

- 상단 헤더 높이를 미리 확보한다.
- 본문에는 해당 화면의 대표 스켈레톤을 배치한다.
- 내부 navigation에서는 가능한 한 페이지 셸이 즉시 스트리밍되도록 한다.
- 루트 `loading.tsx`는 예상하지 못한 상위 지연을 위한 최소 fallback으로 유지한다.

## 6. 단계별 구현 순서

### 1단계: 공통 기반

- `SkeletonBlock`, `SectionLoadingState` 구현
- 색상, radius, pulse 속도 결정
- reduced-motion 처리
- 접근성 검토

### 2단계: PLAN

- `PageHeader`와 데이터 영역 분리
- `PlanGridData` 및 `PlanGridSkeleton` 구현
- 현재 배치 쿼리 횟수가 증가하지 않는지 확인

### 3단계: SEE

- scope 해석과 데이터 loader 분리
- 별자리·통계·회고 Suspense 경계 구성
- loader 공유로 쿼리 중복 방지

### 4단계: DO와 TASKS

- 폼과 목록을 섹션 단위로 스트리밍
- 기존 필터 동작과 URL query 보존

### 5단계: HOME

- 관측소 단일 스켈레톤 적용
- 첫 슬라이드 우선 로딩은 별도 성능 변경으로 평가

## 7. 검증 기준

### 기능

- 기존 화면 데이터, 정렬, 필터 결과가 동일하다.
- 다른 사용자의 계획·할 일·기록이 노출되지 않는다.
- 빈 상태와 오류 상태가 스켈레톤 뒤에 정상 표시된다.
- 직접 URL 접근과 `Link`를 통한 soft navigation이 모두 정상 동작한다.

### 성능

- soft navigation에서 `PageHeader`가 DB 본문보다 먼저 표시된다.
- 로컬 개발 모드가 아닌 production build에서 측정한다.
- 모바일과 데스크톱 각각 LCP를 측정한다.
- 목표 LCP는 p75 기준 2.5초 이하다.
- 페이지별 DB 쿼리 수가 변경 전보다 증가하지 않는다.
- 스트리밍 도입 전후 서버 전체 완료시간도 함께 기록한다.

### 시각 안정성

- 스켈레톤에서 실제 콘텐츠로 전환할 때 큰 레이아웃 이동이 없다.
- 카드 grid의 열 수와 gap이 실제 화면과 동일하다.
- 별자리 및 통계 영역의 최소 높이가 유지된다.
- 밝은 배경에서 스켈레톤 대비가 지나치게 강하지 않다.

### 접근성

- 섹션당 로딩 상태 안내는 한 번만 제공한다.
- 장식용 스켈레톤은 스크린리더에서 숨긴다.
- 키보드 포커스가 로딩 완료 시 임의로 이동하지 않는다.
- reduced-motion 환경에서 pulse를 제거한다.

## 8. 완료 조건

- PLAN, TASKS, DO, SEE의 정적 헤더가 데이터 조회와 분리된다.
- 주요 데이터 영역에 섹션 단위 스켈레톤이 적용된다.
- 동일 요청 안에서 중복 DB 쿼리가 발생하지 않는다.
- 타입 검사, 린트, 단위 테스트 및 인증/소유권 통합 테스트를 통과한다.
- production build의 soft-navigation LCP가 변경 전보다 개선된다.
- 결과와 정렬, 권한 경계에 회귀가 없다.

## 9. 이번 범위에서 제외할 항목

- 데이터베이스 스키마 변경
- 새로운 영속 캐시 도입
- 작업 기록 페이지네이션
- 캐러셀 UX 변경
- 디자인 시스템 전면 개편

이 항목들은 스켈레톤과 스트리밍의 효과를 측정한 뒤 별도 변경으로 진행한다.
